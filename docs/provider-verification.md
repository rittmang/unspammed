## Constraints that affect feature parity

- **Vercel:** the checked-in configuration requests a 300-second function and minute cron. Built-in minute scheduling requires Pro/Enterprise; Hobby permits daily cron. Function request/response bodies are limited to 4.5 MB, so Unspammed's larger export allowance is not available for browser responses there. Server-to-server Telegram export delivery follows a different path but still needs time/memory checks. Optional MTProto TCP connections, redirects and saved-account recovery require an actual provider test. [Cron plans](https://vercel.com/docs/cron-jobs/usage-and-pricing), [function limits](https://vercel.com/docs/functions/limitations).
- **Persistent Node hosts:** the timer requires a running process. Render Free spins down after 15 idle minutes. Fly's supplied config disables autostop; keep a running Machine. Railway's separate cron minimum is five minutes, and App Platform's is 15 minutes; neither replaces the application's minute timer. [Render Free](https://render.com/docs/free), [Fly configuration](https://fly.io/docs/reference/configuration/), [Railway cron](https://docs.railway.com/cron-jobs), [App Platform jobs](https://docs.digitalocean.com/products/app-platform/how-to/manage-jobs/).
- **Free-account gates:** Fly's documentation advertises a two-VM-hour/seven-day trial with a forced stop after five minutes; the newly verified test account instead required a card before any Machine could be created. No card was added. Railway trial verification/outbound-network restrictions can prevent external PostgreSQL or Telegram connectivity even after signup. Free or trial signup is not an always-on service guarantee. [Fly trial](https://docs.fly.io/about/free-trial), [Railway trial](https://docs.railway.com/pricing/free-trial).
- **Other containers:** Cloud Run request-based CPU allocation and scaling to zero differ from instance-based billing plus minimum instances. Azure Container Apps can keep `minReplicas >= 1`; an ECS service can keep desired/minimum tasks running. These platforms do not universally stop between requests. A sleeping configuration needs a tested, awaited, authenticated scheduler integration. EventBridge Scheduler targets AWS APIs; arbitrary HTTPS API Destinations are a separate integration with a five-second client timeout. [Cloud Run CPU/billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings), [Azure scaling](https://learn.microsoft.com/en-us/azure/container-apps/scale-app), [ECS scaling](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-auto-scaling.html), [Scheduler targets](https://docs.aws.amazon.com/scheduler/latest/UserGuide/managing-targets-universal.html), [API Destinations](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-api-destinations.html).
- **Netlify:** a future adapter must preserve all private routes, static allowlists, cookies and cron authentication, with work chunks fitting its documented 30-second scheduled-function limit. Its Functions/Postgres support disproves the earlier claim that it cannot run database-backed code. It does not establish Unspammed compatibility. [Functions configuration](https://docs.netlify.com/build/functions/configuration/), [PostgreSQL](https://docs.netlify.com/build/data-and-storage/netlify-database/), [scheduled functions](https://docs.netlify.com/build/functions/scheduled-functions/).

Reverse proxies on every host must preserve paths, Origin, authorization, request-protection headers and Set-Cookie; allow necessary import/export sizes and request durations; and provide trusted HTTPS. Do not expose the bare app port or database port publicly when using the VM proxy. Configuration syntax checks do not verify DNS, certificates, proxy behavior or outbound PostgreSQL/Telegram TCP.

## Adding actual provider evidence

Use a separate test bot/group and disposable database. Record date, source/build identity, provider and test-account scope, plan/runtime, database endpoint type, accepted build, deployed HTTPS/authentication/webhook checks, actual minute ticks and restart recovery, export limits, optional MTProto status and physical-client coverage. Mark each item passed, failed or not run. Keep credentials, session data and real message text out of evidence. Follow the [deployment checklist](deployment.md#verification-checklist); do not turn a successful health request into an unperformed scheduler or Telegram-client claim.
