# Policy improvement

Use **Policy improvement** in the owner dashboard. Feedback now starts an automatic propose → test → revise loop. The page shows one progress/result card and a final **Approve update** action. This improves the editable policy sent to the same classifier; it does not retrain Gemini or Jev. Existing labels remain saved, and the live policy only changes after owner approval.

## Correction → draft

In a message inspector or saved Model lab result, expand **Add reasoned feedback**. Save spam, legitimate, or needs-context/review, a reason code, an optional short explanation, and whether the available context is complete. A family name lets you group related campaigns, copied templates or sources. Variants from the same family count once. Automatic normalized-text grouping is a heuristic; the owner should group semantically related sources too.

Three fresh **actual corrections** in distinct families for the same reason and label queue an automatic improvement run on the next minute tick. Confirming the original decision does not count. Consumed families are not recycled into new automatic runs. One correction remains evidence; it is not a global rule. **Add a policy instruction** can start a run immediately. Generation, reference preparation, testing and revisions occur in the background; no separate draft/test buttons are required. Only one improvement run is processed at a time in each group.

Labels without reasons still update lab ground truth, but do not trigger drafting. Other-policy-boundary feedback needs an explanation. Conflicting labels stay held until explicitly resolved, including after clearing and resubmitting a label. Images, incomplete context, missing original predictions and legacy runs without saved original thresholds are held instead of inventing evidence. Historical labels are not silently converted into correction triggers.

Each feedback event is append-only and binds the original message/context, original policy/model/thresholds, original prediction, owner label/reason and the action state at correction time. Live original prediction snapshots are saved before strikes or manual overrides. Moderation actions remain separate from labels. User identity is never classifier evidence.

## Draft → measured decision

The proposer generates a complete replacement policy with at most three general criteria. It replaces conflicting wording, keeps unrelated wording unchanged and cannot include concrete message quotations, URLs or user references. Unchanged and duplicate proposals stop the run without more replay calls. Jev/Decisions models cannot generate prose, so drafting uses the Gemini Flash Lite fallback; paired classification uses the configured fixed classifier. Provider/model/usage details remain in the saved records, outside the main page. [Jev's typed output](https://openrouter.ai/docs/guides/community/jev).

On a failed performance check, another proposer call receives the previous policy, up to twelve concrete mistakes with owner labels, baseline/candidate predictions and explanations, decision thresholds, and summaries of earlier attempts. It revises semantic criteria and wording rather than memorizing examples or creating keyword/Unicode blacklists. These are model-generated diagnoses, not measured causal feature importance. Up to four candidates are attempted per run. Earlier failed attempts and replay runs remain immutable; the UI shows the latest candidate in the same improvement run. No reliable improvement, repeated wording, insufficient fresh references or an infrastructure failure stops automatic work with a plain-language status.

Each candidate freezes its references automatically. Spam and legitimate labels are enough; available needs-review examples are included, but no ambiguous labels need to be invented to fill a quota. Saved reference counts state the label coverage; a run without review labels does not establish ambiguity-handling quality. Each split needs at least two spam and two legitimate references, spanning five independent families. Thus at least fifteen independent families are needed overall; duplicate classifier inputs and related families stay together. Reference preparation checks feasibility before inference. Sampling is bounded to 120 distinct text/caption references.

Development includes the triggering corrections and prior mistakes. Automatic candidates must fix all triggering corrections and pass development before validation starts; a passing validation starts the final fresh test. Baseline and candidate receive identical message/context snapshots, fixed model, thresholds and protocol. Labels/family/source IDs are not sent to the classifier. When a round fails, exposed examples/families and input hashes become learning-only material for later rounds, with selected mistakes retained for development. Later validation/final checks use fresh examples. Unopened test reservations may be released when abandoning a candidate; exposed tests stay used and cannot become fresh by renaming families. A failed test is never relabelled or rerun as fresh. Source edits, retractions, conflicts or settings changes block stale publication.

Reported separately: automatic spam coverage, spam deferred to review, allowed spam/misses, legitimate messages flagged, appropriate ambiguity reviews, unnecessary legitimate reviews, total review workload, tokens, cost and observed model/provider. Required review examples are always included. The weighted development/validation loss is `ham→spam=10`, `spam→ham=2`, `review→spam=5`, `review→ham=1`, `spam→review=0.5`, `ham→review=0.25`; correct decisions have zero loss. This is a transparent engineering gate, not a calibrated probability or a claim of statistical generalization.

Automatic development and validation must improve weighted loss by at least one. The final fresh test must not increase loss, allowing a perfect baseline to remain perfect. All phases introduce no new false-positive IDs, misses or ambiguity-as-spam IDs, preserve correct required reviews, and add at most floor(5% of reference count) unnecessary legitimate reviews. Inference cost must be known and at most 1.5× baseline. Actual model/provider identities must agree in both paired runs and across phases, and provider configuration/protocol must stay unchanged. Decisions responses can use a documented dated identity for the requested model; the observed identity must still remain fixed. [Decisions response schema](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request).

Unknown billing/identity fails the gate and does not trigger semantic prompt revisions. Provider failures pause the run; **Try again** resumes its saved frozen evaluation cursors or explicitly retries drafting. A partially billed request is not silently duplicated. Failed performance checks trigger the bounded revision loop automatically.

## Approval → Observe → Enforce

Passing both gates enables owner approval of the exact replacement and measured tradeoffs. **Approve update** verifies candidate and parent hashes inside a serialized database transaction, stores a policy version and starts the new policy in Observe. Testing never publishes on its own. Incoming messages are scored and logged without strikes or deletions. Inspect these live results, then enable Enforce in Settings when ready.

The page shows five stages: draft update, test feedback, check fresh messages, final check, and owner approval. It highlights the current stage, shows the revision number and counts completed checks from saved evaluation cursors. Progress reflects the current revision rather than an estimated duration; refining a candidate starts the stages again. Paused or unsuccessful runs stay at the stage they reached, and the last step completes only after approval. The page refreshes automatically while work is active. A short summary of the successful change and optional proposed-policy review accompany approval. Prompt diffs, phase tables, source IDs, token/cost reports and model/provider diagnostics are omitted from the main UI. A compact overview response omits replay diagnostics and learning examples; full saved records remain available for audit and Model lab. Action errors stay beside their action until retried or dismissed; successful refreshes do not clear them.

**Restore version** provides rollback and preserves the current operational mode and limits. A stale settings tab cannot overwrite a newly published policy. If improvement is unclear, keep the current policy. Implementation deployment itself does not approve any candidate or change the current live policy/mode.

## Validation and limitations

The repository tests exercise triggers, immutable provenance, conflicts/idempotency, tri-state gates, feasible reference splits, paired replay, freshness, stale references/settings, provider drift, explicit approval, Observe rollout and rollback. The full lifecycle runs against both the local adapter and a disposable loopback Postgres database. All provider calls in those tests are mocked; no Telegram effects are issued.

A separate real OpenRouter/Gemini smoke used five synthetic text cases and three requests for approximately $0.00047. It verified the draft/classification API paths; its candidate did not pass the improvement gate and was not published. See [provider smoke](improvement-provider-smoke.json). This is not production accuracy evidence or a sealed-test evaluation. Existing community labels were not altered for testing.

Visual pixels are not stored in replay datasets. Image feedback is explicitly held until a visual evidence replay mechanism exists; current image moderation continues independently. Custom endpoints without observed model/provider metadata or known costs cannot pass this conservative approval gate. Model lab and replay provider billing remain uncapped, as requested; live moderation retains its separate daily token budget. Worker plan and billing are unchanged.
